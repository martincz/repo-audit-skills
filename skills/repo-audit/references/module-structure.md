# 代码目录与模块粒度重组蓝图（`Mode R` · 严格只读）

本规程对项目的物理目录结构、模块内聚度与依赖方向执行系统性只读盘点，输出一份 **100% 行为等价、可直接供人工拍板分批落地的《目录与模块重组蓝图》**。

## 1. 严格边界：只读输出蓝图，不改代码逻辑

- **全程只读（`Mode R`）**：不移动、重命名、拆分、合并或编辑任何文件；仅输出完整重组方案。
- **职责正交**：聚焦**物理目录归属、巨石文件拆分、碎片微文件合并与模块单向依赖拓扑**；函数内部的冗余逻辑简化与异常处理修复留给 `references/code-quality.md`，蓝图中所有拆并方案必须以**严守 100% 外部行为、计算口径与接口契约等价**为前提。
- **符号与依赖图优先**：若连接 `Serena`、`codebase-memory-mcp` 或 LSP 工具，优先分析模块导入图、扇入/扇出（fan-in / fan-out）与跨目录引用环路；未连接则通过 AST 或检索梳理模块依赖边。

---

## 2. 模块拆并与目录归整的五条黄金标尺

1. **按业务域与共同闭包归组（拆解万能垃圾桶目录）**
   - 遵循共同闭包原则：因同一业务演进而总是被一起修改的文件归入同一内聚目录。
   - 重点审视语义宽泛的大杂烩目录（如 `utils/`、`helpers/`、`common/`、`misc/`、`shared/`）：仅服务单一业务域的辅助逻辑建议下沉回该业务域；仅真正跨多域复用的无状态底层纯原语保留在公共基础层。
   - 目录层级保持扁平克制（通常 2～3 层），避免设计长期只有 1 个文件的深层空壳目录。

2. **按变化轴正交性拆分，拒绝按行数一刀切（保护深模块）**
   - 不因单文件行数较多就机械拆碎高内聚的「深模块」（避免制造大量跨文件跳转与私有状态暴露）。
   - 仅当满足以下任一条件时才建议拆分：
     - ① 同一文件混杂了不同变化轴的职责（例如：纯领域计算/规则逻辑 + 数据库 SQL/外部 HTTP I/O + 路由/CLI 入口混合在同一文件）；
     - ② 轻量公共常量/数据结构契约与重型运行时依赖（如数据库连接池、重型第三方 SDK）绑死在同一模块，迫使轻量调用方被动引入重依赖；
     - ③ 两个模块相互引用形成双向耦合，需抽离独立的底层契约/类型模块打破环路。

3. **合并过度细碎的浅模块（消除碎片化）**
   - 满足以下任一条件且无独立演进需求时，优先建议合并：
     - ① 全仓仅有唯一宿主调用方、体积微小且脱离宿主无独立领域语义的私有附属文件；
     - ② 仅做参数原样透传或符号重导出、不提供实质抽象隔离的薄包装文件；
     - ③ 同一目录下围绕同一核心对象拆得过散、每次改动都必须同时打开修改的多个微碎文件。

4. **自上而下单向无环依赖（DAG）与纯净包入口**
   - 目标目录依赖必须保持单向无环（典型流向：`入口层 routes/cli/jobs/ui` → `领域服务与核心计算` → `存储与外部基础设施适配` → `基础契约/类型/配置`），彻底识别并消除循环导入（含靠函数体内局部延迟 `import` 掩盖的结构性环路）。
   - 包入口文件（如 `__init__.py`、`index.ts`、`mod.rs`）应保持轻量，不承载导入期网络/磁盘 I/O 或重型全局初始化副作用。

5. **全量盘点“非 import 隐式引用”防断链**
   - 任何拟议的文件移动、重命名、拆分或合并，必须提前在仓库中检索并列出需同步更新的非代码 `import` 字符串引用：
     - 测试用例中的 `mock.patch("...")`、`monkeypatch.setattr("...")` 字符串路径与固定夹具路径；
     - 动态导入（如 `importlib`、动态 `import()`）、插件反射注册、路由字符串加载、ORM 模型发现配置；
     - CLI 入口声明、`pyproject.toml` / `package.json`、`Dockerfile`、CI/CD 与定时调度脚本；
     - 前端模板路径、构建打包配置（如 Tailwind `content` 扫描路径、Vite/esbuild/Webpack 入口与路径别名）；
     - 架构依赖边界测试（如 `test_boundary` 类契约单测）及 `AGENTS.md`、`README.md`、项目级 Skills 中的路径引用。

## 3. 必输交付物：《目录与模块重组蓝图》

报告严格按以下 4 个章节依次输出：

1. **现状核心结构症结（最多 5 条）**
   列出当前最突出的职责错位、巨石混杂、微文件碎片化或循环依赖问题，每条附上真实文件路径与依赖链路证据 `[静态推断]` / `[已实测]`。

2. **目标目录树与单向依赖流向**
   用紧凑的目录树展示调整后的模块职责边界，并标明自上而下的合法依赖方向。

3. **文件变更决策总表与“深模块保留白名单”**
   - **拟变更文件总表（Markdown 五列表格）**：包含 `动作（移动 / 重命名 / 拆分 / 合并 / 清理空壳）` | `原文件路径` | `目标文件路径` | `拆分或合并的具体符号边界与职责依据` | `已检出的隐式引用风险点`。
   - **明确建议不拆的核心深模块（2～3 个）**：单独列出仓库中体积虽大但职责单一高内聚、强行拆分反而有害的核心文件，说明保留理由。

4. **原子分批执行与验证计划**
   将拟变更项划分为若干低耦合、每批均可独立跑通静态检查与对应测试的原子批次（推荐顺序：第 1 批下沉底层公共契约并打破循环依赖 → 第 2 批合并同域碎片微文件 → 第 3 批正交拆解职责混杂巨石文件 → 第 4 批归整入口目录并同步更新隐式引用与文档），明确每批建议使用的保留历史迁移方式（如 `git mv`）与必跑验证命令。
