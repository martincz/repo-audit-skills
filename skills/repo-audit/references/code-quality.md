# 编码健壮性、并发边界与反过度设计审计（`Mode R` · 严格只读）

本规程从**代码逻辑质量与结构复杂度**两端双向审视代码库：一方面揪出隐藏在异常处理、并发竞争与数据边界中的正确性隐患；另一方面砍掉“把简单问题复杂化”的伪扩展与冗余防御，输出可安全落地的代码精炼清单。

## 1. 职责边界与核心判断标尺

- **职责切分**：本规程聚焦**模块与函数内部的控制流、状态一致性、错误处理与抽象层次**；单纯的物理目录归属调整、文件重命名与拆并搬家归 `references/module-structure.md` 负责，不在本报告展开文件迁移图。
- **区分两种复杂度**：
  - **必要复杂度（必须保留）**：为保障资金/核心业务口径准确、并发原子一致、崩溃幂等恢复、安全隔离或真实外部协议兼容而存在的保护逻辑。
  - **非必要复杂度（重点精简）**：为臆想中未发生的未来需求、上游类型/契约已保证绝不可达的状态、或单次调用薄透传而堆砌的抽象层、兜底分支与配置项。
- **防误判铁律**：静态检索或符号图谱未查到直接调用方不等于死代码。在判定任何抽象、分支或配置“无调用方/冗余”前，必须核查动态导入、装饰器/注册表、反射、框架生命周期钩子、模板渲染与外部配置文件引用，并在证据中注明已排查范围。

## 2. 六大检查维度（每类输出 0～3 条最高价值问题）

### 板块一：编码正确性、并发与异常健壮性

1. **异常吞没、伪造兜底与失败语义失真**
   - 捕获宽泛异常（如裸 `except Exception` / `catch`）后静默忽略，或在本应快速失败（Fail Fast）的不可恢复故障上直接返回 `0` / `[]` / `None` 伪装成“正常无数据”，导致下游静默算出错误业务结果或污染持久化状态；
   - 多步状态变更或外部副作用中途抛错时，缺乏回滚或补偿标记，使业务对象卡在不可恢复的中间半截状态。

2. **并发竞态、资源生命周期与精确边界缺陷**
   - 多线程/多协程/多实例共享可变全局缓存或内存字典却缺乏同步保护，或存在非原子“先查后写（Check-Then-Act）”竞态漏洞；
   - 金额、费率、清结算等精确数值误用二进制浮点数（`float`）累加比较，跨时区时间运算混用 Naive 与 Aware 时间对象，或空集合/除零/极值边界未闭合；
   - 文件句柄、网络连接、流式响应、数据库游标或后台异步任务在异常分支下未正确关闭取消，存在泄漏风险。

### 板块二：非必要复杂度与过度设计减法

3. **过度抽象与伪扩展性**
   - 全仓仅有唯一具体实现且无明确近期多实现计划的接口/抽象基类/策略工厂/注册中心；
   - 不提供任何领域语义转换或参数收敛、仅做原样参数透传的多层薄包装函数或代理类；
   - 为“以后也许支持动态插件/多引擎”而提前编写但从未启用的复杂泛型脚手架。

4. **内部可信链路重复防御与冗余兜底**
   - 入口边界或类型系统已完成强校验的不变量，在内部私有调用链每一层反复重复判空、类型转换与格式防御；
   - 为上游逻辑已彻底排除的不可达状态编写大量死兜底分支，干扰阅读者对真实业务契约的判断。

5. **状态与控制流过度复杂（多真相源）**
   - 原本可用清晰线性数据流或单一枚举表达的生命周期，被拆散为多个相互纠缠的布尔标志位（如 `is_ready` + `has_loaded` + `is_error` 组合爆炸）；
   - 同一业务状态在内存多个对象或上下游冗余字段中重复维护并手工同步，极易产生状态漂移。

6. **配置开关包袱与重复造轮子**
   - 从不调整的内部实现常量被过度暴露为环境变量/配置项，或为早已下线的旧版本长期保留兼容死分支；
   - 手写脆弱代码重复实现语言标准库或项目现役核心依赖已原生提供的高可靠能力（如手写重试器、LRU 缓存、路径解析、CSV/URL 编解码等）。

## 3. 单条问题格式与双表收尾要求

每条问题按以下定制结构输出：
- **问题标题** `[已复现]` / `[已实测]` / `[静态推断]`
- **涉及位置**：具体文件路径 / 类或函数符号
- **现状表现与代码证据**：简明描述当前隐患或多余封装，附上全仓调用点核查、上游不变量证明或动态引用排查依据
- **收敛/修复方案**：说明修复缺陷或砍掉冗余后的目标精简形态
- **前提与风险边界**：修改前需确认的假设，防止简化过头误伤真实边界保护
- **投入产出比**：收益（高/中/低）× 改动成本（低/中/高）

全部维度结束后，固定输出两部分收尾：
1. **分阶段治理与简化清单（表格）**：按「高收益低成本（优先落地）→ 关键正确性加固（近期安排）→ 中等结构瘦身（顺手收敛）→ 暂缓项」排序，每项一句话写明理由与切入函数。
2. **明确建议保留的必要复杂点（2～3 条）**：列出项目中看似复杂、但承担核心正确性/安全/幂等职责而不应删减的关键逻辑，为后续重构划定保护红线。
